C++ Memória Dinâmica (new e delete)

Na aula Como a Memória Funciona, você viu que o heap é um depósito onde o programa pede espaço durante a execução, e que o std::vector faz isso por você. Nesta aula você vai pedir e devolver esse espaço com as próprias mãos, usando new e delete. E vai ver, com os relatórios reais de uma ferramenta de diagnóstico, os três erros clássicos que isso permite. O objetivo é entender o que acontece por baixo; no fim, você vai ver por que o C++ moderno quase não usa new direto.

Você vai aprender
  • Como pedir um valor ao heap com new int e devolver com delete.
  • Como pedir um array de tamanho decidido na execução, new int[n], e devolver com delete[].
  • O que é um vazamento de memória, e como o AddressSanitizer o encontra.
  • O que acontece ao usar memória depois de devolver (heap-use-after-free).
  • O que acontece ao devolver duas vezes (double free).
  • Por que, no C++ moderno, você vai preferir std::vector e ponteiros inteligentes.

Os programas foram compilados na máquina fictícia da Ana (usuária ana, computador notebook), na pasta ~/cpp, com g++ -std=c++23 -Wall -Wextra arquivo.cpp -o programa. Para os erros de memória, a aula usa também -g -fsanitize=address, o AddressSanitizer (ASan), que tem aula própria em Sanitizers. Os relatórios dele são longos; aqui aparecem só os trechos importantes, e os cortes estão marcados com …. Os sanitizers rodam no terminal, com o g++ ou o clang++; o editor do guia não os tem.

A ideia: um depósito de aluguel

Pense numa empresa de boxes de aluguel. A Ana chega no balcão e diz: "preciso de um box". O atendente reserva um e entrega um papel com o número do box. Quando ela não precisar mais, devolve a chave no balcão, e o box fica livre para outra pessoa.

No depósitoEm C++
Alugar um boxnew int: reserva espaço no heap e devolve o endereço (um ponteiro).
O papel com o número do boxO ponteiro que guarda esse endereço: int* p = new int;
Devolver a chavedelete p;
Esquecer de devolver: paga para sempreVazamento de memória (memory leak).

Na pilha, o compilador aluga e devolve sozinho, a cada { e }. No heap, com new, quem devolve é você. Toda a dificuldade desta aula vem daí.

1. new e delete: um valor

#include <iostream>

int main() {
    int* p = new int(42);        // pede ao heap espaço para um int, com 42 dentro

    std::cout << "p  = " << p << "\n";
    std::cout << "*p = " << *p << "\n";

    *p = *p + 1;
    std::cout << "*p = " << *p << "\n";

    delete p;                    // devolve o espaço ao heap
}
new int(42)
Pede ao heap espaço para um int, guarda 42 nele e devolve o endereço. Sem os parênteses (new int), o valor inicial seria lixo; com new int() ou new int{}, seria 0.
int* p = …
O endereço vai para um ponteiro comum. O int que mora no heap não tem nome: o único jeito de chegar até ele é pelo p.
*p
Lê e muda o valor, exatamente como na aula Ponteiros.
delete p;
Devolve o espaço. Depois disso, p continua guardando o mesmo endereço, mas ele não vale mais: o box foi devolvido.
$ g++ -std=c++23 -Wall -Wextra um.cpp -o um
$ ./um
p  = 0x57b8de7fa020           « um endereço do heap (não começa com 0x7ff…)
*p = 42
*p = 43

Esta figura é a chave de tudo. Se o p sumir antes do delete, o int do heap fica lá, alugado, sem ninguém que saiba o endereço dele. Isso é o vazamento, que você vai ver na seção 3.

Missão: peça ao heap um int com o valor 2026, guarde o endereço em ano, mostre Ano: 2026 pelo ponteiro e devolva a memória no fim.

#include <iostream>

int main() {
    // int* ano = ...

    // mostre "Ano: " e o valor apontado

    // devolva a memória
}

#include <iostream>

int main() {
    int* ano = new int(2026);
    std::cout << "Ano: " << *ano << "\n";
    delete ano;
}

2. new[] e delete[]: um array de tamanho variável

Um array comum (int notas[5]) precisa ter o tamanho escrito no código. Com new, o tamanho pode vir de uma variável, decidido durante a execução, por exemplo digitado pelo usuário:

#include <iostream>

int main() {
    int quantidade = 0;
    std::cout << "Quantos alunos? ";
    std::cin >> quantidade;

    int* notas = new int[quantidade]{};   // tamanho decidido na execução; {} zera tudo

    for (int i = 0; i < quantidade; ++i) {
        notas[i] = 10 - i;
    }
    for (int i = 0; i < quantidade; ++i) {
        std::cout << "Aluno " << i + 1 << ": " << notas[i] << "\n";
    }

    delete[] notas;              // array: delete com colchetes
}

$ g++ -std=c++23 -Wall -Wextra varios.cpp -o varios
$ ./varios
Quantos alunos? 3               « a Ana digitou 3
Aluno 1: 10
Aluno 2: 9
Aluno 3: 8
new int[quantidade]
Pede espaço para quantidade inteiros colados, e devolve o endereço do primeiro. Daí em diante, notas[i] funciona como num array (aula Ponteiros e Arrays).
{}
Zera todos os itens. Sem ele, cada item começaria com lixo.
delete[] notas;
Devolve o array inteiro. Os colchetes avisam: "isto foi pedido com new[]".
Par certo: new com delete, new[] com delete[]

Misturar os dois é comportamento indefinido. O g++ às vezes percebe e avisa:

int main() {
    int* notas = new int[5]{};
    delete notas;                // deveria ser delete[]
}

$ g++ -std=c++23 -Wall -Wextra mistura.cpp -o mistura
mistura.cpp: In function ‘int main()’:
mistura.cpp:3:12: warning: ‘void operator delete(void*, long unsigned int)’ called on pointer returned from a mismatched allocation function [-Wmismatched-new-delete]
    3 |     delete notas;                // deveria ser delete[]
      |            ^~~~~
mistura.cpp:2:29: note: returned from ‘void* operator new [](long unsigned int)’
    2 |     int* notas = new int[5]{};
      |                             ^

"operator delete chamado num ponteiro que veio de uma função de alocação que não combina", e a nota mostra que ele veio de operator new []. Com o ASan, a execução para com alloc-dealloc-mismatch (operator new [] vs operator delete).

3. Vazamento de memória: esqueceu o delete

A função abaixo é chamada a cada venda da lojinha. Ela pede 400 bytes (100 ints) e esquece de devolver:

#include <iostream>

void registrar_venda() {
    int* itens = new int[100];   // pede 400 bytes
    itens[0] = 1;
    std::cout << "Venda registrada\n";
    // esqueceu o delete[] itens;
}

int main() {
    registrar_venda();
    registrar_venda();
    registrar_venda();
}

$ g++ -std=c++23 -Wall -Wextra vazamento.cpp -o vazamento
$ ./vazamento
Venda registrada
Venda registrada
Venda registrada

Nenhum aviso, nenhum erro, tudo "funcionou". É isso que torna o vazamento traiçoeiro. Mas veja o que aconteceu: a cada chamada, o ponteiro itens (que mora na pilha) morreu no } da função, e os 400 bytes do heap ficaram alugados, sem ninguém que saiba o endereço. Ninguém mais consegue devolvê-los. Com três vendas, são 1200 bytes perdidos; num programa que roda o dia inteiro (um servidor, um jogo), a memória usada só cresce, até a máquina ficar lenta ou o sistema matar o programa.

O AddressSanitizer inclui um detetive de vazamentos, o LeakSanitizer, que confere tudo quando o programa termina:

4. Usar depois de liberar (use after free)

Depois do delete, o ponteiro continua guardando o endereço antigo. Nada impede o programa de seguir esse endereço, e é aí que mora o perigo:

#include <iostream>

int main() {
    int* saldo = new int(500);
    delete saldo;

    std::cout << "Saldo: " << *saldo << "\n";   // usa depois de devolver!
}

$ g++ -std=c++23 -Wall -Wextra depois.cpp -o depois
$ ./depois
Saldo: 66794023                « nem 500, nem erro: lixo
$ echo $?
0

Compilou sem aviso, rodou sem cair e mostrou um saldo de 66 milhões. O heap já tinha reaproveitado aquelas casas para as suas anotações internas. Num programa de verdade, o box devolvido pode já ter sido alugado para outra parte do programa, e escrever nele estraga dados de outra pessoa. Esse tipo de defeito é uma das falhas de segurança mais exploradas em programas escritos em C e C++.

Com o ASan, o erro é pego na hora, com três endereços de linha: onde foi o uso, onde foi devolvido e onde foi pedido:

5. delete duas vezes (double free)

#include <iostream>

int main() {
    int* p = new int(7);
    std::cout << "*p = " << *p << "\n";
    delete p;
    delete p;                    // devolve de novo a mesma memória
    std::cout << "Fim\n";
}

$ g++ -std=c++23 -Wall -Wextra duas.cpp -o duas
$ ./duas

Quem percebeu foi a própria biblioteca do sistema (a glibc), que administra o heap: "free(): liberação dupla detectada". O free é a função de baixo nível que o delete usa; o tcache é uma das listas internas onde ela anota os boxes livres.
Abortado
A biblioteca matou o programa de propósito (o sinal SIGABRT, "abortar"), porque o heap ficou num estado em que não dá para confiar. Em inglês: Aborted (core dumped).
134
128 + 6, o número do SIGABRT. O Fim nunca apareceu.

O hábito: zerar o ponteiro depois do delete

Um delete num nullptr não faz nada, e um ponteiro nulo pode ser testado (aula nullptr). Então, logo depois de devolver, apague o endereço do papel:

#include <iostream>

int main() {
    int* p = new int(7);
    delete p;
    p = nullptr;                 // o papel agora diz "nenhum endereço"

    if (p == nullptr) {
        std::cout << "p não aponta mais para nada\n";
    }
    delete p;                    // delete em nullptr não faz nada: é seguro
    std::cout << "Fim\n";
}

$ g++ -std=c++23 -Wall -Wextra zerar.cpp -o zerar
$ ./zerar
p não aponta mais para nada
Fim

Isso ajuda, mas não resolve tudo: se existir uma cópia do ponteiro (int* q = p;), ela continua com o endereço velho. É por isso que a solução de verdade é não ter delete escrito à mão.

6. E se o heap não tiver espaço?

Se o pedido for grande demais, o new não devolve um ponteiro nulo: ele lança uma exceção chamada std::bad_alloc ("alocação ruim"). Para mostrar sem travar a máquina, a Ana limitou a memória do terminal a cerca de 500 MB com ulimit -v e pediu 4 GB:

#include <iostream>

int main() {
    std::cout << "Pedindo 4 GB...\n";
    int* p = new int[1'000'000'000];
    std::cout << "Consegui!\n";
    delete[] p;
}

$ g++ -std=c++23 -Wall -Wextra gigante.cpp -o gigante
$ ulimit -v 500000              « limita a memória deste terminal (em KB)
$ ./gigante
Pedindo 4 GB...
terminate called after throwing an instance of 'std::bad_alloc'
  what():  std::bad_alloc
Abortado                   (imagem do núcleo gravada) ./gigante
$ echo $?
134

"Encerrado depois de lançar uma std::bad_alloc": ninguém tratou a exceção, então o programa abortou. Num programa comum, você raramente vai tratar esse caso; o importante é saber que new nunca devolve nullptr por falta de memória (salvo com a forma especial new (std::nothrow)). O ulimit -v vale até você fechar o terminal.

7. Por que o C++ moderno quase não usa new

Você viu três erros graves, e nenhum deles foi pego pelo compilador. Agora imagine um programa com centenas de new, funções com vários return no meio, exceções que pulam o delete... Garantir que cada new tenha exatamente um delete, no momento certo, é muito difícil. Por isso a regra do C++ moderno é: quem pede a memória é um objeto que sabe devolvê-la sozinho.

O varios.cpp da seção 2, sem nenhum new:

#include <iostream>
#include <vector>

int main() {
    int quantidade = 0;
    std::cout << "Quantos alunos? ";
    std::cin >> quantidade;

    std::vector<int> notas(quantidade);   // o vector pede e devolve sozinho

    for (int i = 0; i < quantidade; ++i) {
        notas[i] = 10 - i;
    }
    for (int i = 0; i < quantidade; ++i) {
        std::cout << "Aluno " << i + 1 << ": " << notas[i] << "\n";
    }
}                                         // sem delete: nada para esquecer

$ g++ -std=c++23 -Wall -Wextra vetor.cpp -o vetor
$ ./vetor
Quantos alunos? 4
Aluno 1: 10
Aluno 2: 9
Aluno 3: 8
Aluno 4: 7

O std::vector faz o new[] por dentro e o delete[] no } em que ele morre, sempre, mesmo que a função saia por um return no meio ou por uma exceção. Essa técnica de "o objeto devolve no fim da vida dele" se chama RAII e tem aula própria: Destrutores e RAII.

Você precisa de…Em vez deUse
Uma lista de tamanho variávelnew int[n] / delete[]std::vector<int>
Um textonew char[n]std::string
Um objeto no heap, com um dononew Produto / deletestd::unique_ptr com std::make_unique
Um objeto no heap, com vários donosnew e contar "na mão"std::shared_ptr com std::make_shared

Então por que aprender new e delete? Porque eles estão por baixo de tudo isso, porque você vai encontrá-los em código antigo e porque entender os três erros desta aula é o que faz os ponteiros inteligentes (próxima aula) fazerem sentido.

Quando dá errado

O programa usa cada vez mais memória (vazamento)

O que aconteceu: algum new não tem o delete correspondente, muitas vezes porque a função saiu antes (um return no meio, uma exceção) ou porque o ponteiro foi sobrescrito.

Como resolver: compile com -g -fsanitize=address, rode até o fim e procure as linhas Direct leak of … allocated from:; a primeira linha com um arquivo seu (/home/ana/…) é o new culpado. Depois troque esse new por std::vector ou std::make_unique.

Valores absurdos depois de um delete (heap-use-after-free) 
$ ./depois
Saldo: 66794023

O que aconteceu: o programa leu memória que já tinha sido devolvida. Sem sanitizer, o sintoma é lixo, ou uma queda bem longe do erro de verdade.

Como resolver: o ASan mostra três linhas: o uso (READ/WRITE), o freed by e o previously allocated by. Mova o uso para antes do delete e zere o ponteiro (p = nullptr;). Melhor: use um ponteiro inteligente.

"free(): double free detected" e "Abortado" (134) 
$ ./duas
*p = 7
free(): double free detected in tcache 2
Abortado                   (imagem do núcleo gravada) ./duas

O que aconteceu: o mesmo endereço foi devolvido duas vezes, às vezes por duas cópias do mesmo ponteiro.

Como resolver: cada new tem um dono, responsável pelo único delete. É exatamente o que o std::unique_ptr garante.

"called on pointer returned from a mismatched allocation function" 
$ g++ -std=c++23 -Wall -Wextra mistura.cpp -o mistura
mistura.cpp: In function ‘int main()’:
mistura.cpp:3:12: warning: ‘void operator delete(void*, long unsigned int)’ called on pointer returned from a mismatched allocation function [-Wmismatched-new-delete]
    3 |     delete notas;                // deveria ser delete[]
      |            ^~~~~
mistura.cpp:2:29: note: returned from ‘void* operator new [](long unsigned int)’
    2 |     int* notas = new int[5]{};

O que aconteceu: memória pedida com new[] foi devolvida com delete (sem colchetes), ou o contrário.

Como resolver: new ↔ delete, new[] ↔ delete[]. Ou std::vector, que não tem como errar.

Resumo

  • new pede memória ao heap e devolve um ponteiro; delete devolve. Para arrays: new T[n] e delete[].
  • O ponteiro mora na pilha e some sozinho; a memória do heap só some com delete.
  • Vazamento: esqueceu o delete. Nada aparece; o LeakSanitizer acusa Direct leak of … bytes.
  • Usar depois de liberar: mostra lixo ou corrompe dados; o ASan acusa heap-use-after-free.
  • Liberar duas vezes: free(): double free detected, Abortado, código 134.
  • Depois de delete p;, faça p = nullptr;. Melhor ainda: não escreva delete.
  • No C++ moderno, use std::vector, std::string e ponteiros inteligentes. Próxima aula: Ponteiros Inteligentes.
